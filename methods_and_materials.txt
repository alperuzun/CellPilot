# Methods

## Background

Single-cell RNA-sequencing (scRNA-seq) studies routinely measure tens of thousands to millions of cells per experiment, and a complete computational pipeline — quality control, normalization, dimensionality reduction, clustering, cell-type annotation, and downstream interpretation — is now standard practice [1, 2]. Although mature open-source libraries implement the core operations, assembling them into a reproducible end-to-end workflow remains the domain of bioinformaticians rather than the wet-lab researchers who generate the data. Cell-type annotation in particular has no canonical solution: marker-database scoring, atlas-trained classifiers, ensemble methods, and curated marker panels each address different sources of label uncertainty, and analysts in practice run multiple methods and reconcile their outputs manually. A third source of friction is the round-trip between visual inspection and statistical follow-up in notebook-based workflows, which discourages the kind of fine-grained iterative curation that produces accurate cell-type calls.

CellPilot is a desktop application that integrates a complete scRNA-seq analysis pipeline, seven complementary annotation backends with majority-vote consensus, on-demand differential expression, subclustering with merge-back, and a context-aware large-language-model assistant into a single locally installed tool. The remainder of this section describes the implementation, the analysis pipeline, the annotation engine, and the interactive curation workflow.

## Implementation

### Architecture

CellPilot is implemented as three loosely coupled tiers (Fig. 1). The presentation tier is an Electron desktop client written in TypeScript and React, with interactive plots rendered using Plotly.js. The application layer is a local FastAPI / Uvicorn HTTP service that exposes the analysis pipelines as background jobs and streams progress to the renderer. The computational tier comprises a Python scRNA-seq stack centred on Scanpy [1] and AnnData [2], extended with OmicVerse [9] (which provides pySCSA [3] for marker-database scoring), Scrublet [10], CellTypist [6], PopV [7], scVI / scANVI [11, 12], and mLLMCelltype [8]. The three tiers run as coordinated processes on the user's machine and are launched together by a shell script that activates the Conda environment, starts the API server, and opens the Electron client.

### Software stack

The desktop client is built on React 19 and Electron, packaged with electron-forge and bundled with Vite. UI styling combines Tailwind CSS and Material-UI; interactive scientific plots are produced with Plotly.js. The backend is implemented on FastAPI with Pydantic-typed request and response schemas. Two-dimensional embeddings are produced with UMAP [15] and Minimum-Distortion Embedding (MDE) [16]; community detection is performed with the Leiden algorithm [14] via `leidenalg` and `igraph`. The full dependency graph is pinned in a single Conda environment specification.

### Local-first deployment

All computation is performed locally. Datasets, intermediate files, and outputs are written to the user's filesystem; no telemetry or cloud round-trip occurs. The only optional outbound traffic is to user-configured large-language-model (LLM) provider endpoints when the AI assistant or LLM-based annotation backend is invoked, in which case only the prompt context (cluster summaries, marker tables) is transmitted; the underlying expression matrix is never sent. This deployment model addresses three constraints in scRNA-seq analysis: regulatory restrictions on cloud upload of patient-derived material (e.g., dbGaP, EGA, IRB-controlled datasets); the operational overhead of provisioning and maintaining a Python environment for non-bioinformatics users; and the per-job compute footprint of methods such as PopV, which is awkward to share through a multi-tenant web service but tractable on a single workstation.

### Output organization

Each analysis run writes its outputs to a timestamped directory of the form `output/{name}_{YYYYMMDD_HHMM}/`, containing the resulting AnnData object, all generated figures (PNG at 300 DPI by default; SVG and PDF where applicable), per-method confidence reports in plain text and JSON, and the parameter set used for the run. Sub-runs (e.g., subclustering jobs) are written to nested directories under the parent run, preserving lineage information in the directory hierarchy.

## Input and preprocessing

### Input formats

CellPilot accepts 10x Genomics Cell Ranger feature-barcode matrices (`filtered_feature_bc_matrix.h5`) and pre-computed AnnData objects (`.h5ad`). Datasets that already contain normalized counts, highly variable genes, principal components, a *k*-nearest-neighbor graph, and a UMAP embedding can be flagged by the user as preprocessed; the wizard then bypasses the upstream stages and proceeds directly to annotation (Fig. 2a). On upload, an index-only validation pass — which reads the AnnData metadata without loading the expression matrix — records cell count, gene count, available `obs` columns, and pre-existing embeddings, and presents these to the user before the analysis is launched.

### Quality control

Cells are filtered on three criteria with user-configurable thresholds: minimum detected genes per cell (default 250), minimum total counts per cell (default 500), and maximum fraction of mitochondrial counts (default 5%; mitochondrial-gene prefix configurable, defaulting to `MT-` for human or `mt-` for mouse). Pre-filter QC violin plots of total counts, detected genes, and mitochondrial fraction are generated automatically to support threshold selection. Doublet detection is performed with Scrublet [10] using its default sensitivity parameters, and identified doublets are removed in the same pass that applies cell-level filters. The number of cells removed by each criterion is recorded in a per-run QC summary.

### Normalization, feature selection, and clustering

Raw count matrices are preserved in a dedicated AnnData layer prior to normalization to support downstream operations that require the unmodified counts. Counts are then total-count normalized to 10,000 per cell and log-transformed (log1p). Highly variable genes are selected with the Seurat-v3 procedure [17] (default *n* = 2000), and the full normalized matrix is retained in the `.raw` slot to support marker-gene queries on genes outside the highly-variable panel. The HVG-restricted matrix is scaled to unit variance and zero mean (clipped at ten standard deviations) and reduced with principal component analysis (default 50 components). A *k*-nearest-neighbor graph is constructed on the principal components (default *k* = 15) and partitioned with the Leiden algorithm [14]. Because the appropriate clustering resolution is dataset-dependent, Leiden partitions are precomputed at a panel of resolutions (default 0.3, 0.5, 0.8, 1.0, 1.5, 2.0) in a single pass and stored as separate `obs` columns; the dashboard's Resolution Explorer enables post-hoc switching between them without re-running the algorithm. Two embeddings are produced for visualization: a UMAP layout [15] and a Minimum-Distortion Embedding [16]. Per-cluster marker genes for every resolution are precomputed using the Wilcoxon rank-sum test [1] and cached.

## Cell-type annotation

The annotation engine executes any user-selected subset of seven complementary backends on the same dataset and computes a per-cluster majority-vote consensus across them (Fig. 3). Each backend exposes a uniform interface that returns per-cluster labels, per-cluster confidence scores, and any output artifacts to be persisted with the run. The uniform interface enables consensus computation at the orchestrator layer regardless of the underlying methodology — logistic-regression classifier, marker-database enrichment test, or LLM call — and permits new backends to be added without modifying the consensus logic.

### Marker-database scoring

Three backends — CellMarker 2.0 [4], PanglaoDB [5], and the Cancer Single Cell Atlas — share the pySCSA scoring statistic [3] as exposed by OmicVerse [9]. For each Leiden cluster, marker genes derived from the precomputed Wilcoxon test are tested for enrichment against each cell type in the chosen reference using a *z*-score-based statistic. The cell type with the highest score is assigned to the cluster, and confidence is reported on a five-level scale (High / Medium / Low / Ambiguous / Unknown) derived from the gap between the top score and the runner-up, with category boundaries calibrated to flag clusters whose top assignment is not robustly separated. The three references differ in coverage rather than in scoring methodology: CellMarker 2.0 covers a broad range of human and mouse tissues; PanglaoDB provides species-spanning markers including for less-common cell types; the Cancer Single Cell Atlas focuses on tumor-associated populations.

### Atlas-trained classifier

CellTypist [6] is a logistic-regression framework trained on curated single-cell atlases. Pretrained models, downloaded automatically into a local cache on first use, are selected by the user according to the tissue of interest. The framework returns a per-cell probability matrix; per-cell predictions are smoothed by *k*-nearest-neighbor majority voting on the embedding to mitigate per-cell label noise. Cluster-level labels are obtained by averaging per-cell probabilities across each Leiden cluster and assigning the top class. Confidence is graded from the cluster-mean probability of the top class together with its margin over the runner-up, with category thresholds set to flag low-probability or low-margin assignments as Ambiguous.

### Ensemble classifier

PopV [7] runs eight independent classifiers and reports their majority vote together with an integer agreement score ranging from 0 (full disagreement) to *n*<sub>classifiers</sub> (full agreement). The constituent classifiers are *k*-nearest-neighbor classifiers over BBKNN, Scanorama, scVI [11], and Harmony [13] embeddings; a random forest; a support vector machine; scANVI [12]; OnClass [18]; and CellTypist. PopV is launched in a separate subprocess to isolate its memory footprint from the API server; on macOS, the subprocess is invoked with `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES` to suppress fork-safety errors from the underlying frameworks. The default reference is the Tabula Sapiens HuggingFace HubModel [19]; arbitrary annotated AnnData objects can be substituted as custom references for tissues or species not represented in the default. The agreement score is exposed as an additional confidence channel orthogonal to the majority-vote label, allowing clusters with weak inter-classifier agreement to be flagged for manual review.

### Manual marker annotation

User-supplied marker gene lists, provided as CSV (one row per `{cell_type, gene}` pair) or as free text, are scored per cell using the Scanpy `score_genes` routine [1]. Each cell is assigned the cell type with the highest score, with cells below a configurable threshold (default 0.1) labelled "Unknown."

### LLM-based annotation

mLLMCelltype [8] queries one or more LLMs with the precomputed top marker genes per cluster (default top 10) together with user-supplied tissue and species context, returning a structured cell-type call and the model's reasoning. Two operating modes are exposed: a single-model mode and a consensus mode in which several models are queried independently and their outputs are reconciled through an iterative discussion protocol with a configurable agreement threshold (default 0.7) and a bounded number of rounds (default 3). LLM-derived labels are flagged as advisory in the user interface and are reported alongside, never replacing, the calls from the marker-based and atlas-based backends. API keys for OpenAI, Anthropic, Gemini, and OpenRouter are managed through the in-app Settings panel and stored in a local environment file; each key is validated at the time it is entered by issuing a minimal probe request to the corresponding provider.

### Consensus

When two or more backends are run in the same job, the orchestrator computes a per-cluster majority vote across their outputs. Both the consensus label and the fraction of methods agreeing on the winning label are stored as `obs` columns; the agreement fraction serves as the consensus confidence and is used to color the consensus channel on the embedding. Clusters with full agreement display uniform confident coloring, while disagreement clusters carry an immediate visual flag for manual review. Per-method labels are preserved as separate `obs` columns to support downstream comparison, and the consensus is recomputed whenever the set of backends is modified. A simple majority vote was selected over a learned reconciliation model on three grounds: interpretability, the absence of dataset-specific hyperparameters, and graceful degradation when individual backends fail or are skipped.

## Subclustering

Heterogeneous clusters can be refined through an integrated subclustering workflow (Fig. 4). The user defines a subset of cells either by selecting a parent cluster or by drawing a freehand lasso, configures resolution and annotation backends for the sub-run, and submits the job. The application reverts to the stored raw counts for the selected cells — rather than the parent-run normalized matrix — and re-executes the preprocessing pipeline (normalization, log transformation, HVG selection, scaling, PCA, neighborhood graph, Leiden clustering, embedding) on the subset. Returning to the raw counts is necessary because HVGs selected on the parent dataset are dominated by genes that vary across major populations, not by genes that vary within a sub-population, and re-running HVG selection on the subset surfaces the within-subset axes of variation. The number of principal components is automatically capped at min(*n*<sub>cells</sub> − 1, *n*<sub>HVGs</sub>, requested) to handle small subsets robustly.

After re-clustering, the subset is re-annotated with the user-selected backends. Per-cell methods (CellTypist, PopV) are skipped because their per-cell labels are determined by gene expression and are unchanged on a subset of the same cells; cluster-level methods (marker-database backends, mLLMCelltype, manual markers) are re-run because re-clustering exposes new sub-populations. Sub-run results are written to a nested output directory under the parent run, and refined labels can be merged back into the parent dataset's `obs` as a new annotation layer. Merge-back aligns by cell barcode rather than positional index to remain correct across intervening edits.

## Differential expression

Differential expression on user-defined cell groups is supported in three modes (Fig. 5). The **global** mode compares a selection against all remaining cells; the **local** mode compares a selection against the cells in the same Leiden cluster but outside the selection, controlling for cluster identity; and the **selection-vs-selection** mode compares two independently defined groups. A minimum group size is enforced to ensure statistical stability. Tests are implemented through Scanpy's `rank_genes_groups` using the Welch *t*-test with overestimated variance (`t-test_overestim_var`) and `pts=True` to recover per-group expression fractions. Results are reported as ranked gene lists with log<sub>2</sub> fold change, raw and Benjamini–Hochberg-adjusted *p*-values, mean group expression, and per-group expression percentages, and are rendered in the dashboard as volcano plots, top-up / top-down dot plots, and tabular outputs. The Welch test was selected over more sophisticated negative-binomial models (e.g., DESeq2-style) for the interactive path on grounds of latency: the *t*-test runs in real time as the lasso selection is redrawn, preserving interactive responsiveness. Final-figure differential expression with more rigorous models can be performed offline on exported AnnData subsets.

## Interactive exploration and iterative annotation curation

The visualization dashboard is the primary user-facing surface of the application and the locus of the iterative curation that produces final cell-type annotations (Fig. 7). High-quality annotations require multiple rounds of inspection, hypothesis testing, and refinement; in notebook-based workflows the round-trip latency between cells dominates total session time and limits the number of iterations the analyst attempts. The dashboard collapses every operation in the curation loop into a single view, eliminating cross-cell context switches.

### Layout

The dashboard is organized as a canvas with a UMAP or MDE embedding at center, a left rail of canvas tools (pan, zoom, lasso), a context-aware right inspector, a top bar of global controls, and a slide-up bottom drawer hosting the marker-gene heatmap, QC violin plots, dot plots, and volcano plots. The right inspector is the principal mechanism by which separate operations remain coupled: when no selection is active it displays global dataset statistics; on cluster selection it displays the cluster's marker genes, per-method labels, consensus confidence, and quality metrics in a single pane; on lasso selection it displays the selection's composition together with one-click handoffs to differential expression, the AI assistant, the subclustering wizard, and the annotation editor. The active selection is shared across all panels, eliminating manual transfer of cell-index lists between operations.

### The curation loop

Curation sessions follow a four-phase iteration. **Inspection** consists of switching the embedding's color-by channel between Leiden clustering, per-method annotations, the consensus column, and the consensus-confidence column; clusters with low confidence or strong inter-method disagreement are visually distinct and become candidates for review. **Hypothesis** consists of clicking on a candidate cluster and reading its top marker genes, per-method labels, and consensus agreement fraction in the right inspector. **Test** has three sub-flows, each appropriate to a specific question: (i) a freehand lasso paired with the local-mode differential-expression test addresses whether a sub-population is statistically distinct from the remainder of its parent cluster (Fig. 5); (ii) the Resolution Explorer's small-multiples grid addresses whether the cluster is over-merged or over-split at the current resolution; (iii) a query to the AI assistant in cluster or selection mode (Section "AI bioinformatics assistant" below) provides an independent label hypothesis grounded in the marker table the analyst is inspecting (Fig. 6). **Refinement** consists of committing an edit through the Annotation Manager (rename, reassign, merge), launching a subclustering sub-run for genuinely heterogeneous clusters (Fig. 4), or extending the manual marker panel and re-running the manual backend. The cycle then returns to inspection.

### Annotation layers and provenance

Edits made during curation are committed as named AnnData `obs` columns rather than as in-place modifications of a single label column. Multiple co-existing layers (e.g., a baseline `consensus_annotation`, a first-pass `consensus_curated_v1`, and a final `final_celltypes`) preserve the provenance of every iteration and can be revisited or compared at any point. Layer creation, cloning, renaming, and per-cluster or per-cell label edits are exposed through the Annotation Manager. Because layers are first-class `obs` columns, all downstream operations reference them: subclustering jobs use the active annotation column to define parent clusters, the AI assistant's prompt context includes all detected annotation layers, and selection-vs-selection differential expression can be run between groups defined on a curated layer.

### Figure export

The Publication Export modal renders the active embedding to PNG, SVG, or JPEG with user-configurable resolution, palette, axis labels, and font sizes. Exporting from within the dashboard ensures consistency between the view used during curation and the figure included in the manuscript and removes the duplication of plotting code that arises when figures are generated from a separate script.

## AI bioinformatics assistant

CellPilot includes a conversational analysis assistant operating on the dataset currently open in the dashboard (Fig. 6). The assistant is implemented as a chat sidebar backed by a pluggable LLM provider layer with current support for OpenAI and Anthropic models; Gemini and OpenRouter slots are scaffolded for future expansion. The assistant operates in three context modes. In **global** mode the prompt context comprises a structured dataset summary (cluster sizes, top marker genes per cluster, per-method annotations, global QC metrics) and the assistant addresses questions of overall composition. In **cluster** mode the context is restricted to the currently selected Leiden cluster and includes that cluster's marker genes, QC metrics, and per-method labels. In **selection** mode the cells inside an active lasso define the scope, and the prompt context includes the selection's compositional breakdown across all detected annotation columns, QC metrics, and most highly expressed genes.

The system prompt instructs the model to ground all claims in the supplied marker tables and quality metrics and to cite published evidence (paper plus author and year, or consortium reference) where appropriate. Grounding the assistant in the prompt context shifts its operational role from biological oracle to interpreter of supplied data, mitigating the confabulation risk of unconstrained LLM use. A "blind analysis" mode (`hide_labels=True`) suppresses all annotation columns from the prompt, requiring the model to reason from markers and expression alone; this mode is intended as an independent label hypothesis that does not anchor on the upstream pipeline. Provider keys are stored in a local environment file and are read only at the moment of an LLM call. The assistant is positioned as advisory: it does not write to the AnnData object, and any cell-type call the user wishes to commit must be entered through the Annotation Manager. This separation preserves user responsibility for the final label set and prevents silent propagation of LLM errors into manuscript figures.

## Configuration, reproducibility, and data security

All Python dependencies are pinned in a Conda environment specification, producing a deterministic environment on macOS (Apple Silicon and Intel) and Linux. Output directories are timestamped and contain (i) the resulting AnnData object; (ii) all generated figures at 300 DPI; (iii) per-method confidence reports as JSON and plain text; (iv) a QC report; and (v) the run parameter set. Random seeds for the underlying libraries (Scanpy, UMAP, Leiden, scVI / PopV, Scrublet) inherit upstream defaults; users requiring strict numerical reproducibility may pin seeds explicitly through the wizard's advanced-parameters interface. The conversational assistant is non-deterministic by design (LLM sampling); each prompt context is logged alongside the response to support session-level traceability. LLM API keys, when configured, are stored only in a local environment file and are not written to logs or transmitted outside the user-selected provider's API. GPU acceleration via PyTorch CUDA is optional and is used by PopV and scVI when an NVIDIA GPU is detected.
